One bug, three clouds, and a fix that fools the demo

October 11, 2026 · Andrew Arrow · Updated October 12

Move "Join the waitlist" to the top of our little editor, hit Save, and everything looks fine. The button is still there. The editor says "Saved." Reload the page and the button disappears. Three blocks went in; two came back. Apparently the first one was a tip.

We planted this bug on purpose. We also wrote a patch that looks like it fixes the bug while doing absolutely nothing about the data loss. It makes a perfectly good demo, right up until someone touches refresh.

You can try the broken editor without an account. It's the first test case for Repo Rodeo, a project we're building to take a GitHub issue and a reproduction recipe, get the app running, and give independent coding agents their own copies to repair. A maintainer should be able to open the broken app, open a proposed repair, repeat the same actions, and inspect the diff. That's useful even if every agent whiffs.

First, though, the harness has to catch our deliberately bogus fix. We took the same experiment to Mainbrella, E2B, and Daytona. All three now get the browser controls right. Mainbrella restores the files and needs fresh servers; E2B copies the running servers too. Daytona got through its three restores on a rerun after our first capture timed out, although its post-delete preview responses still fail our strict cleanup check.

We build Mainbrella, so one of these providers is ours. It contributed a 403, an exhausted workspace quota, and some awkward storage accounting to the investigation. No provider gets a speed trophy here, and no coding agent has attempted the repair yet.

The bug fits in two lines

The editor keeps the document in memory and writes a serialized copy to localStorage. The serializer assigns positions from the array index, then filters them:

blocks
  .map((block, position) => ({ ...block, position }))
  .filter(block => block.position);

Zero is falsy. Goodbye, first block. The storage write succeeds, so the UI announces "Saved" and keeps showing the untouched in-memory draft. JavaScript has done exactly what we asked, which is rude but fair.

Moving the button to the top makes the damage obvious. Saving in the original order loses the heading instead. Below is the same document just after Save and after a browser reload. The heading and paragraph survive; the button doesn't.

The correct patch removes the filter. The misleading patch adds one line after saving:

localStorage.setItem(storageKey, JSON.stringify(serialized));
setStatus('Saved');
render(); // The misleading patch adds only this line.

That render() redraws the same healthy-looking draft already in memory. Nothing reads the stored document back. A video that ends at Save can look great with either patch, and a screenshot can't tell them apart. The reload is the part that makes the fix earn its keep.

If our verifier accepts the bad patch, plugging in a cleverer agent just gives us a more persuasive wrong answer. So the browser test reads the ordered block IDs and their text before Save, after Save, and after reload. Looking for "Join the waitlist" somewhere on the page would be a lousy substitute. The help text could contain those words while the document had already eaten the button.

A red test can mean your test is broken

There are three answers the verifier can give: passed, reproduced, and unverified. That third one gets a lot of exercise once a cloud provider joins the party.

To call the bug reproduced, the verifier requires the intact document before reload and exactly that document minus its first block afterward. Same remaining IDs, same order, same text. A timeout, an HTTP error, a missing test, or an unrelated assertion doesn't count. Neither does a run with skipped or retried tests. If the baseline is unverified, the experiment stops before trying either patch.

The recorded standalone run gets the answers we want:

That one passing baseline check is deliberate. Reset has to restore the demo without nuking unrelated browser storage. The test plants another localStorage key containing keep me and checks that it survives. Sprinkling localStorage.clear() over a persistence bug would be a pretty spectacular way to make the demo work at everyone else's expense.

We also save without reordering, edit the text, and reload through both the browser and the editor's "Reload saved" button. The randomized holdout makes six documents, shuffles their blocks, and runs each through two reloads. Its strings include blanks, Unicode, <&>, both kinds of straight quotes, and varying amounts of repeated text. Give a serializer something more annoying than "Hello, world" and see whether it's still feeling confident.

The random seed is recorded, so those twelve reloads are repeatable. A passing patch gets through all twelve; the broken cases stop at the first loss. They're extra cases for this editor's persistence behavior, with known answers. We aren't calling twelve reloads an agent benchmark. Both patches are deterministic, and the verifier runs outside the writable app copies, where a repair can't casually edit its own exam.

Now every branch needs to start with the same broken app. Getting that app into a browser turned out to be its own debugging project.

First, get the broken app to actually break

Our first Mainbrella attempt didn't lose a button. It returned HTTP 403.

We had archived a pinned checkout of this website, uploaded it through the file API, installed the dependencies in a container, and started Vite. Mainbrella forwarded the guest Host header as container, which Vite didn't allow. The machine was up. The server was up. The browser still couldn't reach the damn editor.

Adding that exact host to the experiment's launcher got us through. The launcher also set the local API address explicitly, so the copied website wouldn't default to the production API. These changes belonged to the launch setup; the host checkout stayed untouched. The run notes keep the failed attempt alongside the working one.

Once the baseline reproduced the loss, we needed three independent copies of the prepared app: unchanged, correctly patched, and misleadingly patched. Installing dependencies belongs in the common starting point. Applying a patch belongs in one branch. Otherwise we're making every attempt repeat setup work and hoping nothing changes between installs.

The local deployment offered saved workspaces, with native filesystem forking and memory preservation disabled. We tried saving the files, then restoring them into fresh containers. The first capture got HTTP 429, workspace_quota_exceeded. The account reported 100 saved workspaces against a limit of 20. Well, there's your problem.

We left those workspaces alone and continued the manual experiment with a disposable account and a synthetic trial entitlement in local D1. That exercised capture and restore through the same API, but bypassed signup and payment. The tracked adapter later hit the same exhausted quota in its local preflight and stopped before provisioning. No quietly deleting somebody's old workspaces to make the test green.

The files survived. Did the server?

One saved workspace supplied all three branches. Each kept the checkout, lockfile, and installed dependencies, so none needed another npm ci. A different marker file in each branch stayed private to that branch; the source had none of those markers.

But a directory full of files can't tell us whether the running server came along. A PID alone isn't enough either: a freshly started process can reuse the same number. Our launcher creates a tiny probe once, when the server starts:

const probe = {
  nonce: randomUUID(),
  pid: process.pid,
  startedAt: new Date().toISOString()
};

The server returns it from /__rodeo_process with Cache-Control: no-store. The endpoint serves the nonce generated at process startup; it never loads an old nonce from disk. If a restored server answers with the source's nonce and PID before we launch anything, we have evidence that it inherited that process state. If nothing is listening, we need to start a server and check its new nonce.

On Mainbrella, the source's nonce stayed the same through capture. Each restored container initially refused connections; explicitly starting Vite produced a fresh nonce in each one. The diagram shows the files branching while the source process keeps running.

For this bug, that's fine. The app needs its code and dependencies on disk, and the external browser can recreate the document. The browser's localStorage isn't inside the server container anyway. Forking the server doesn't fork the person using it.

A half-processed in-memory queue would be a different story. Restarting that server might erase the very condition we wanted an agent to investigate. "Copy the environment" is a bit hand-wavy when one version copies a running process and another hands you files and says to start over.

The production Mainbrella run confirmed the same behavior through the tracked adapter, using the same pinned web revision and seed as the E2B and Daytona cloud workloads. The account had room for four containers and one saved workspace; no synthetic entitlement was needed. The filesystem checks covered source hashes, the installed dependency lockfile, marker contents, permission bits, and a symlink target. A directory existing is a low bar for "restored."

All three restored controls behaved as expected through their protected previews. The correct patch passed all six checks, including twelve holdout reloads. After the other branches finished, each branch still had its own marker and expected source hashes, and the source was unchanged.

E2B brought the running server along

E2B found a different way to give us a running sandbox with no usable app. The base template had Node 20.9.0, which lacked crypto.hash, required by our pinned Vite build. Installing Node 22.22.2 didn't immediately fix it: the login shell kept selecting the old version.

The setup notes record each attempt. We installed the pinned binary from the official Node distribution, checked its SHA-256, and set the command's PATH explicitly. This console capture shows .profile sourcing .bashrc when Bash is running. Having the right binary on disk and executing the right binary are, annoyingly, separate accomplishments.

Then authenticated HTTP readiness returned 200 while Chromium got 403. Our browser helper authenticated the first request but mishandled the redirect chain. The first retained cloud result correctly stopped before capture or repair attempts. Six red tests on a forbidden page tell us nothing about the button.

The helper now follows a bounded number of same-origin redirects and keeps the preview token scoped to that origin. Slapping the token onto every browser request would have been an easy fix, with the small downside of handing it to whatever other host the page visits.

With that fixed, the follow-up run reproduced the baseline and made one native fork request for three branches, each with an explicit thirty-minute lifetime. All three inherited a listening server, the source's nonce, and its PID. That's the behavior E2B documents for its memory-preserving fork, and the process probe let us observe it.

The source and three branches were alive together in this capture: four concurrent sandboxes in the console header, with htop open in the source sandbox.

After checking inherited state, we stopped those copied servers and launched fresh ones for patch verification. That kept the repair checks repeatable while still testing whether the fork preserved the running process. Our external browser wasn't forked; each test reconstructed the document in a fresh context.

The baseline and misleading patch lost the first block. The correct patch passed. After all branches finished, their markers and source hashes still matched the expected independent repairs. We now had two successful cloud experiments with different process behavior, which is much more useful than collapsing both into a checkmark next to "forking."

Memory preservation also doesn't promise that a client's connection survives. E2B's fork documentation says it pauses the source during capture and drops active connections. A server can remember what it was doing while the terminal watching it gets disconnected. Anything running the experiment has to cope with both.

Lose the reply without losing the workspace

A repair attempt shouldn't depend on keeping one laptop, browser tab, or event stream alive. In the manual Mainbrella run, a new browser recovered an eight-second managed job after the original browser closed. Production exercised the API path: disconnect the SSE stream after its first message, make a new client, recover the same execution ID and exit status zero, then read the remaining output from the saved cursor.

E2B also recovered the same background command and retained guest output with a new SDK client. Its saved position is a byte offset in the guest log; Mainbrella's is an SSE event cursor. Both recovered this workload. Production login and dashboard session recovery weren't part of the Mainbrella API check.

Losing a capture reply is nastier. The cloud may have saved the workspace while the client never learned its ID. A blind retry could create a second workspace, leaving the first one sitting there with nobody claiming it.

So in production Mainbrella we deliberately threw away a successful capture response. The runner had already saved the exact request body and idempotency key to disk. It waited for successful HTTP headers, discarded the response body, then retried with that same body and key. A further replay returned the same workspace again. Three requests, one workspace, one capture reservation.

This is a narrow test on purpose. It covers a completed save whose response body was lost. It doesn't establish what happens if the connection dies while capture is still running. An earlier manual attempt aborted after 150 milliseconds without proving the server had admitted the request; successful headers gave this run a definite point at which to lose the reply.

We didn't run that check on E2B or Daytona. Their adapters have no documented keyed replay guarantee, so they don't reissue an uncertain create or fork. Caching a result in our client wouldn't prove that the cloud deduplicated anything. It would just make the client very confident about its own paperwork.

Cleanup retries need that journal too. Mainbrella records the account, API origin, and container creation timestamp, so an old cleanup command can distinguish its container from a replacement using the same slot. Its adapter also supports a rotated key for the same account; E2B and Daytona recovery currently require their original keys. The adapter guide covers those restrictions; key rotation wasn't an extra cloud scenario we ran.

Daytona got through the rerun

Our early Daytona container fork request got HTTP 422. We'd asked the wrong kind of sandbox to do the trick. The class-specific docs are explicit: container forks aren't supported. The details panel identifies ours as a Container, with its resources and lifecycle settings alongside.

A container snapshot captures files and requires a stopped source. VM memory capture is a separate path, so we switched the container experiment to snapshots.

The first snapshot run got further. It installed the app, passed the type check, and reproduced the five expected browser failures. Capture then exceeded our original three-minute deadline while the API reported snapshotting. This screenshot is from that first attempt: the Snapshots table shows the Repo Rodeo snapshot still in that state.

Timing out our client didn't cancel the provider's work. Deleting the source at that point returned 409. A later inventory showed an active snapshot, but deleting it returned 403: the key could create and delete sandboxes without permission to delete persistent snapshots. We had permission to make the mess and insufficient permission to clean it up.

The source's thirty-minute lifetime didn't apply to the snapshot. A later read-only reconciliation found both exact resource IDs absent from the API and complete inventories. It didn't establish why they disappeared, and it didn't check preview access or physical storage. We kept the original failed result. Eventually getting an active snapshot didn't retroactively give that attempt three tested restores; those needed another run.

The adapter now checks write and delete scopes for both sandboxes and snapshots before creating anything. It saves the exact snapshot name before submission, submits once, and polls that name separately within a ten-minute capture window. If the deadline expires, capture stays uncertain; later inventory observations get another record. The October 12 rerun exercised that revised workflow with the required permissions.

We also rechecked the retained baseline artifacts. The five first-block-loss failures and passing reset check were valid, even though capture failed afterward. New results save that baseline immediately and leave source integrity unchecked until the final comparison runs. Losing the rest of an experiment is annoying enough without throwing away the part that worked.

On the rerun, one capture took about 34 seconds and supplied all three restores. Our adapter stopped the source before capture and restarted it afterward, then launched fresh servers in the source and branches. The retained result verifies the files, installed dependencies, branch isolation, and the same browser outcomes as Mainbrella and E2B: the correct repair passed all six checks, while the baseline and misleading patch each reproduced the five expected failures.

A new Daytona SDK client also recovered the same session and command IDs, exit status zero, and retained stdout after the original polling client detached. That tests recovery from saved output; it doesn't test a dropped live stream or server-side SSE replay. Keyed mutation replay remains unsupported by our adapter and wasn't attempted.

The source restart gave us another useful observation. An old preview token returned 401 while a fresh token returned 200 at the same URL. The app was there; the old credential no longer got you in. That matters when interpreting the cleanup result, because a 401 alone can't tell us whether the sandbox still exists.

Deleted is doing a lot of work here

Mainbrella removed all four test generations and the saved workspace; their old bearer previews returned 404. A separate inventory check confirmed the deletions and that the account's pre-existing container was still there.

E2B's deleted previews returned 502 instead, with or without their traffic tokens. Treating any 502 as successful deletion would let an ordinary gateway outage pass our cleanup check. We first confirmed the exact sandbox IDs absent from the API, then probed every preview three times, two seconds apart, both with and without its token. All 24 follow-up requests returned 502. The probe record supports a provider-specific check that application access ended. It doesn't establish that the tokens were independently revoked.

Daytona's rerun deleted all four run-owned sandboxes and its snapshot. The independent inventory check found each exact resource absent and all thirteen pre-existing snapshots preserved. Immediately after deletion, the five retained preview probes returned 401, 401, 401, 404, 404. Later authenticated probes returned four 401s and one 404; unauthenticated probes all returned 401. Access was denied, but the adapter requires 404 or 410 after API-confirmed absence. That response-code check is the sole reason the overall result still says failed.

Those API and preview checks still don't tell us when physical storage gets reclaimed. In the earlier local Mainbrella run, deleting the test containers and two saved workspaces released their live quota, but two unattached Docker snapshot images remained. We haven't established when those get collected.

Production made the accounting distinction visible too. Its capture reported 258,985,091 bytes, roughly 259 MB, while reserving the full requested 8 GB disk. Here's what the API counters did around that one capture and its deletion; GB are decimal:

So "259 MB captured," "8 GB reserved," and "workspace deleted" can all be true, and none tells you the unique physical bytes or the actual bill. The result keeps those numbers separate. Turning them into one tidy storage number would be bullshit.

We keep cleanup history separate too. Before sealing the evidence, the runner preserves a copy of its request journal. A cleanup retry can extend the live journal without rewriting the original result. Raw traces, screenshots, and request receipts stay private because preview URLs can carry bearer credentials; the public files contain structured document observations. That means the public bundle helps inspect the findings but can't independently rerun the verifier's full decision.

How I'd rank this workflow

I'd put Mainbrella first for completing and recovering this repo's full workflow, followed by E2B and Daytona. For branching a running environment, E2B takes first. Those judgments depend on what we need the harness to do and what our adapters have actually demonstrated. Daytona's third place is provisional because our preview acceptance rules differ by provider.

All three used the same application archive and patch hashes, the same browser checks, and the same random seed. All three produced the same repair outcomes: the correct patch passed all six tests; baseline and misleading repairs reproduced the bug. The differences are in how we copy the environment, recover interrupted work, and confirm cleanup.

Ranking for the demonstrated Repo Rodeo workflow, not a speed or price ranking
RankProviderFor this workflow
1MainbrellaMost complete operational result: restores, isolation, capture replay, SSE recovery, accounting, and preview cleanup checked.
2E2BStrongest live branching: all three forks inherited the listener, PID, and memory nonce. No keyed mutation replay demonstrated.
3DaytonaRestores, isolation, output recovery, and resource deletion succeeded. Capture stopped the source; the strict preview check remains unresolved.

Mainbrella's strongest result is recovery when the client loses track of something the cloud already did. We discarded a successful capture response, retried the same key, and recovered one workspace with one reservation. We disconnected an SSE client and recovered the same execution and remaining output. Cleanup removed every test generation and workspace, preserved the existing container, and returned 404 for every old preview. Those are useful things to have nailed down before letting a repair attempt run unattended.

E2B has the capability Mainbrella is missing here. Mainbrella kept the source server running through capture, but every restored branch needed a fresh process. E2B copied the running listener, PID, and nonce into all three branches. If initialization is expensive or the bug lives in memory, that's a meaningful advantage. We haven't measured a startup saving for those workloads, but we did observe the state a filesystem restore leaves behind.

Daytona's third place is provisional, and its failed label overstates the functional gap. Its resources were deleted and the probes were denied access. Our acceptance rules let E2B pass with repeated 502s plus exact API absence, while Daytona's 401s remain outside its stricter rule. E2B also got more repeated probes. We owe Daytona a consistent follow-up that checks the same outcome with enough evidence, rather than treating the two labels as a clean measure of provider reliability. The 401 alone isn't proof of deletion, as the source-restart check already showed.

Speed and price stay unranked. The retained runs took about 81 seconds on E2B, 203 on Mainbrella, and 238 on Daytona. Those are whole-run totals, each from one run, with different allocations, runtimes, capture mechanisms, and recovery checks. E2B reported two vCPUs and 512 MiB of memory; Mainbrella requested half a vCPU and 4 GiB; Daytona reported one vCPU and 1 GiB. Mainbrella's guest ran Node 24.21.0; the others used 22.22.2. We didn't measure resource enforcement, actual charges, or physical storage reclamation. A latency leaderboard from this would still be nonsense.

Volumes, warm pools, E2B's filesystem-only snapshots, pause/resume, and Daytona VM memory snapshots still need separate experiments. So do agents and pull-request publication. The pinned Daytona SDK also brings an unresolved high-severity dependency advisory; this workload used archive uploads and container snapshots, not its glob-based image builder. Passing our planted bug doesn't qualify this harness to run arbitrary untrusted repositories.

You can run the standalone controls from the repository with its pinned Node 22.22.2:

npm ci
npx playwright install chromium
npm run experiment -- --seed 12345

That command writes a fresh evidence directory with the inputs, patches, document observations, traces, screenshots, and cleanup record. It contacts no cloud provider. The provider run guide has the cloud commands if you want to repeat those workloads with your own credentials.

For a dependable repair workflow, Mainbrella has the strongest demonstrated foundation in these runs. E2B is ahead on the capability I'd most like Mainbrella to add next: cloning a live environment. A bug involving a half-processed background job would give that difference a proper workout. Restarting the server until the symptom disappears is awfully tempting when you can't copy the process that went wrong.
