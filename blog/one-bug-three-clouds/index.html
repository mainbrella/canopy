One Bug, Three Clouds: Building Repo Rodeo

October 11, 2026 · Andrew Arrow · Updated October 12

Move “Join the waitlist” to the top of the editor, hit Save, and everything looks fine. The button is still there. The editor says “Saved.” Reload the page and the button disappears. Three blocks went in; two came back.

You can try the broken editor without an account. We planted this bug deliberately. It gives Repo Rodeo a small, repeatable failure while we build the machinery for handling somebody else’s GitHub issue.

The product we want takes an issue and a reproduction recipe, prepares the application, then gives independent coding agents their own copies to repair. A maintainer should be able to open the broken app, open a proposed repair, repeat the same actions, and inspect the diff. Getting both apps into the browser would be useful even when every agent fails.

Before adding agents, we need to know that the experiment can reject a bad repair. The same deterministic controls now pass in production Mainbrella and E2B: the correct patch preserves the document, and the misleading one still loses a block. Daytona reproduced the baseline, but its snapshot outlived our capture deadline and none of its restored controls ran. The failures in getting there have been at least as useful as the passing runs.

A patch that looks fixed

The editor holds the current document in memory and saves a serialized copy to localStorage. Its serializer assigns positions from the array index, then filters them:

blocks
  .map((block, position) => ({ ...block, position }))
  .filter(block => block.position);

Zero is false, so the first block gets thrown away. The storage write succeeds, which earns the “Saved” message, while the editor continues displaying its untouched in-memory draft. Moving the button makes the loss easy to see. Saving in the original order loses the heading instead.

These captures show the preview in the broken editor immediately after saving and after a browser reload. The same heading and paragraph survive; the button doesn’t.

The correct patch removes the filter. The deliberately misleading patch adds render() after saving, leaving the serializer alone. It redraws the document that’s already in memory, so a demonstration that ends at Save looks perfectly healthy. Reload still loses the first block.

That bad patch is useful. If our verifier accepts it, adding a cleverer agent just gives us a more persuasive wrong answer. The browser test therefore compares ordered block IDs and text before Save, after Save, and after reload. Looking for “Join the waitlist” somewhere on the page would be too weak; help text could contain the words while the document had lost the button.

The suite also saves without reordering, edits the text, checks that Reset leaves unrelated browser storage alone, and generates fresh documents from a recorded random seed. The seed makes the randomized case repeatable. These are checks of this editor’s persistence behavior, with known answers, rather than a score for an agent’s ability to repair unfamiliar code.

Saved files, fresh servers

This mattered in the first Mainbrella run. We archived a pinned checkout of this website, uploaded it through the file API, installed its dependencies in a container, and started Vite. The browser reached the protected preview and got HTTP 403. The experiment hadn’t reproduced the bug. It hadn’t even reached the editor.

Mainbrella forwarded the guest Host header as container, which Vite didn’t allow. Adding that exact host to the run’s launcher got us to the application. The launcher also set the local API address explicitly so the copied website wouldn’t default to the production API. Those were changes to the experimental launch setup; the host checkout stayed untouched. The run notes retain the failed attempt along with the working one.

Once the baseline reproduced the loss, we wanted three independent copies of that prepared application. Installing dependencies belongs in the common starting point. A patch belongs in one branch. The deployment advertised saved workspaces but disabled native filesystem forking and memory preservation, so we tested saving the files and restoring them into fresh containers.

The first capture request hit another obstacle: HTTP 429, workspace_quota_exceeded. The account reported 100 saved workspaces against a limit of 20. We left those workspaces alone. The manual experiment continued with a disposable account and a synthetic trial entitlement in local D1. That let us test capture and restore through the same API, but it tells us nothing about signup or payment.

One saved workspace then supplied the baseline, correct-patch, and misleading-patch branches. All three retained the checkout, lockfile, and installed dependencies. None needed another npm ci. A different marker file in each branch stayed private to that branch, and the source had no marker file.

Keeping the files was only half the question. The running server exposed a random nonce held solely in process memory. Its nonce stayed the same across capture. Each restored container initially refused connections; explicitly starting Vite produced a fresh nonce in each one. The files survived. The running servers had to be started again.

For this bug, a fresh process works fine. The interesting state is code on disk and a document the external browser can reconstruct. A bug involving a half-processed in-memory queue would need a different experiment. Calling both operations “copy the environment” would hide precisely the difference we’re trying to measure.

The same six browser checks ran outside all the containers, through each branch’s protected preview, with a fresh browser context per test. The restored baseline and misleading patch reproduced the loss. The correct patch passed, including all twelve reloads in the seeded holdout. The public observation bundle lets you inspect the recorded documents. Raw traces and screenshots remain private because the preview URLs carry bearer credentials; the public bundle alone can’t rerun the verifier’s full decision.

Taking the same experiment to production

Turning that manual recipe into a tracked adapter didn’t make its result carry over. The adapter’s first local preflight found the same exhausted workspace quota and stopped before provisioning. We then ran the tracked command against api.mainbrella.com, where the account had room for the source, three branches and one saved workspace. Production also advertised saved workspaces, with native filesystem forking and memory preservation disabled. No synthetic trial or entitlement was needed.

The production run used the same pinned web revision and random seed as the E2B and Daytona cloud workloads. One dependency install supplied all three restores. The source server kept its nonce and PID through capture; the restored servers each started fresh. Baseline and misleading repair reproduced the five specific failures, while the correct repair passed all six checks, including twelve holdout reloads. After every branch finished, its marker and expected source hashes still matched, and the source remained unchanged.

Then we deliberately threw away a successful capture response. The runner had already saved the exact request body and idempotency key to disk. It waited for successful HTTP headers, discarded the response body, and retried with that same body and key. A further replay returned the same workspace again. Three requests had produced one workspace and one capture reservation.

The discarded body would have told the client which workspace it had just saved. Both later requests recovered that same identity:

This tests a completed save whose response body was lost. It doesn’t establish recovery from a disconnect while the provider is still capturing. The earlier manual test aborted a client after 150 milliseconds without proving admission; successful headers gave this run an observable point at which to lose the reply.

A repair attempt also needs to outlive the client watching it. In the manual run, a new browser recovered an eight-second managed job after we closed the original browser. Production exercised the API version: disconnect the SSE stream after the first message, create a new client, recover the same execution ID and exit status zero, then read the remaining output from its saved cursor. Production login and dashboard session recovery weren’t part of that check.

Recovery also needs to know what it’s allowed to delete. The Mainbrella adapter binds its journal to the authenticated account and API origin, and records each container’s creation timestamp as well as its slot. That keeps a later cleanup from deleting a replacement that happens to reuse the slot. A rotated key for the same account can recover the run; a different account cannot adopt its records. These are adapter safeguards, with separate tests, rather than additional production scenarios we ran.

E2B kept the running server

E2B gave us another way to reach a running machine without reaching a reproduced bug. Its console showed a running sandbox and process start and exit messages during setup. These are the Level and Message columns from that console capture:

The initial E2B run notes explain the setup failures. The template’s Node version was too old for the pinned Vite build. Installing Node 22.22.2 and setting the command’s PATH explicitly got the server running. The filesystem view makes the shell startup files inspectable: this capture shows .profile sourcing .bashrc when Bash is running. Installing a binary doesn’t by itself settle which one a login shell selects.

Authenticated HTTP readiness eventually returned 200, but Chromium followed a redirect and received 403. Our browser helper had authenticated the first request without handling the redirect chain correctly. The first retained cloud result stopped before capture or repair attempts. The helper now follows a bounded number of same-origin redirects and keeps the preview token scoped to that origin. Giving the browser a token for every host would have fixed one failure by introducing a credential leak.

After fixing authenticated redirects, the follow-up run got through the baseline and made one native fork request for three branches, each with an explicit thirty-minute lifetime. Each branch inherited a listening server, the source’s process nonce, and its PID. We stopped those inherited servers and started fresh ones for patch verification. That lets us test E2B’s memory-preserving fork while keeping the repair checks repeatable. Our external browser wasn’t forked; it reconstructed the document in a fresh context for each test.

The terminal capture belongs to that run’s source sandbox. Its header shows four concurrent sandboxes while htop is open: the prepared source and the three branches were alive together.

The verifier then got the same answers as the local controls: the baseline and misleading patch lost the first block, and the correct patch passed all six checks, including twelve holdout reloads. Each branch kept its own marker and expected source hashes after the others finished. A new SDK client also recovered the same background command and its retained guest output after a stream disconnect. Its saved position is a byte offset in that log, rather than Mainbrella’s SSE event cursor.

Cleanup produced a status code we hadn’t accepted: every deleted E2B preview returned 502, with or without its traffic token. Calling any 502 a successful deletion would be a lousy test. We first confirmed the exact sandbox IDs absent from the API, then made three probes of every preview, spaced two seconds apart, both with and without the token. All 24 follow-up requests returned 502. The probe record supports a provider-specific check that application access ended; it doesn’t establish that the token was independently revoked.

We didn’t run the lost-capture-response test on E2B. Its adapter has no documented keyed replay guarantee, so an uncertain create or fork isn’t reissued. Daytona has the same restriction. Recovery for both currently requires the original API key; rotated-key recovery is unimplemented. Keeping those limitations explicit beats turning a cached local result into supposed evidence that the cloud deduplicated a request.

Daytona’s capture outlived our deadline

Daytona’s setup makes the sandbox class worth checking before asking it to fork. The details panel in this capture identifies a Container, with one vCPU, 1 GiB of memory, 3 GiB of disk, and private preview access. Its lifecycle settings are visible alongside those resources.

Our early container fork request was rejected with HTTP 422. The class-specific guides matter: container forks are unsupported, while a container snapshot captures files and requires a stopped source. VM memory capture is a different experiment. We stopped trying to make the container path impersonate it.

The separate snapshot run installed the app, passed its type check and reproduced the five expected browser failures. Capture then exceeded our original three-minute deadline while the API reported snapshotting. Deleting the source at that point returned 409. A later inventory showed an active snapshot, but deleting that returned 403: the key could create and delete sandboxes without having permission to delete the persistent snapshot. The source’s thirty-minute lifetime didn’t apply to its snapshot.

The later read-only reconciliation found both exact resource IDs absent from the API and from complete inventories. It didn’t establish why they disappeared, and it didn’t recheck preview access or physical storage. We kept the original failed result unchanged. A snapshot eventually becoming active, then disappearing, supplies none of the three restore results we were trying to collect.

The adapter now checks write and delete scopes for both sandboxes and snapshots before creating anything. It records the exact snapshot name before submission, submits once, and polls that name separately, within a ten-minute capture window. An expired capture stays uncertain; later inventory observations go into another record. That revised workflow hasn’t had a new cloud run.

We also went back to the retained baseline report and rechecked its artifacts. The five first-block-loss failures and passing reset check were valid, even though the capture failed afterward. New results retain that prepared baseline immediately, and mark source integrity as unchecked until the final comparison runs. A partial run shouldn’t throw away the part we learned, or label a check it never reached as a failure.

What cleanup released

Production Mainbrella removed all four test generations and the one workspace. Their old bearer previews returned 404. A separate read-only inventory check confirmed the deletions and that the account’s pre-existing container was still there. The raw evidence stayed on the host. Public files contain structured document observations; traces, screenshots and request receipts remain private because they can contain preview credentials.

API cleanup and physical reclamation are separate observations. In the earlier local run, deleting the fixture’s containers and two saved workspaces released its live quota, but two unattached Docker snapshot images remained. We haven’t established when those images are reclaimed. Production supplied another distinction: its capture reported 258,985,091 bytes, roughly 259 MB, while reserving the full requested 8 GB disk.

Deleting the workspace returned the live reservation to zero without refunding those capture counters. None of the counters tells us unique physical bytes or the actual bill. The result retains the measured capture size and the accounting values separately.

We preserve a copy of the request journal before sealing a run’s evidence. Cleanup retries can extend the live journal without invalidating that original copy or rewriting the result. The production evidence check rechecked the retained file hashes and browser reports after deletion. It also matched the experiment inputs to the runner commit; the application revision is recorded separately. A Git SHA is useful provenance, but a dirty checkout can contain code that SHA never described.

This is a comparison of observed state and control outcomes. It isn’t a speed or price ranking. E2B reported two vCPUs and 512 MiB of memory; Mainbrella requested half a vCPU and 4 GiB. Guest images also differed: production Mainbrella used Node 24.21.0, while E2B and Daytona used 22.22.2. Resource enforcement and actual charges weren’t measured. The local OrbStack timings are even less comparable: Docker inspection found no matching per-container CPU or memory limits.

Volumes, warm pools, E2B’s filesystem-only snapshots, pause/resume and VM memory snapshots remain separate unrun experiments. No coding agents or pull-request publication took place. Daytona’s pinned SDK also has an unresolved high-severity dependency advisory; this run used archive uploads and container snapshots, not its glob-based image builder. Passing our planted bug doesn’t qualify the harness for arbitrary untrusted repositories.

You can run the standalone controls now from the repository, using its pinned Node version:

npm ci
npx playwright install chromium
npm run experiment -- --seed 12345

The command writes a new evidence directory with the inputs, patches, document observations, traces, screenshots and cleanup record. It contacts no cloud provider. The provider run guide has the commands for repeating the cloud workloads with your own credentials.

Daytona still owes us the three restores. After that, the next bug should come from a repository we don’t control. A missing background worker or a half-processed in-memory queue will make the choice between saved files and a running process much less forgiving.
