Cloudflare D1+R2 buckets for git but github.com FTW

October 11, 2026 · Andrew Arrow

We built Git storage on Cloudflare D1 and R2 so a new Mainbrella user could build an app with version history before they even had a GitHub account. Once that user wants the project on github.com, we should let them move the history there and stop paying us to keep it. The switch needs to preserve the commits, keep GitHub tokens out of the build machine, and leave one destination for new history.

That became a feature in Projects: connect a GitHub repository, move the saved history, and have Builder commit directly to the linked branch. Our first interface asked the user to paste a repository URL. We caught the problem by comparing it with the ChatGPT Codex Connector’s GitHub installation screens, then gave those screenshots to our coding agent for another pass. The storage transfer and the permission flow both deserve a closer look.

A Git repository that outlives its machine

Suppose someone asks Builder for a small expense tracker. The agent writes source in a temporary Linux machine, installs dependencies, and compiles the app. The machine can go away. “Add a CSV export” tomorrow still needs yesterday’s files and history.

Native Git runs inside that Linux machine. We keep a platform-controlled repository outside the application directory and construct its commits from a snapshot supplied by the Worker. Application scripts can edit their own .git; we don’t reuse that copy as the authority for the next save. The snapshot contains validated source, the dependency lockfile, our starter ignore rules, and referenced generated images. Dependencies, compiled output, and environment files stay out of this managed snapshot. The save path and its native Git helper implement that separation.

R2 holds the durable bytes. Source files are addressed by their SHA-256 hash, scoped to the account and project. A source manifest maps filenames to those objects, so browsing source doesn’t need a running machine. Git history uses a separate set of objects under the same project prefix:

build-git/<user>/<project>/
  objects/<sha256>       # source, assets, manifests, evidence
  parts/<sha256>         # chunks of native Git bundles
  bundles/<commit>.json  # bundle manifest

D1 keeps the version records and the current head: which Builder turn saved a version, its Git commit ID, its parent version, the R2 bundle key, and whether the platform’s build check passed. These are two different identities. The hosted version ID identifies a Builder turn; the Git commit ID identifies a Git object. R2’s SHA-256 object names are a third identity, used for storage integrity rather than Git ancestry. The D1 schema makes the distinction explicit.

The save order matters more than the table names. We upload the immutable R2 objects first, checking bundle-part sizes and hashes, then publish the version and head in a D1 batch. A database trigger rejects an insert if its turn is no longer active or its expected parent is no longer the head. D1’s batch transactions cover the database statements; they don’t turn R2 uploads into part of the same transaction. Uploading first avoids advertising a head whose bytes haven’t arrived.

Store the ancestors once

Our first implementation wrote a full-history bundle for every version. It worked, but a conversation with many edits kept uploading the same ancestors. We changed it to save an initial bundle, then increments containing the objects added since the previous commit. An unchanged save reuses its parent’s backing bundle.

A Git bundle contains Git objects and named references. It can be self-contained or require commits the receiver already has. Our bundle manifests record that prerequisite and the previous manifest’s key. The native helper creates increments with the equivalent of this command; PARENT_SHA stands for the previous saved commit:

git -c pack.window=0 -c pack.depth=0 \
    -c pack.allowPackReuse=false \
    bundle create --version=2 next.bundle main ^PARENT_SHA

We split each bundle into parts of at most 1 MiB, hash them with SHA-256, and retain the manifest linking them. A fresh machine reconstructs the chain, clones the initial bundle, fetches the increments, and checks that it reached the expected commit. This is Git doing Git’s object validation; D1 and R2 supply the durable storage around it.

The odd-looking packing options serve downloads. We wanted the Worker to export a self-contained repository without starting a paid sandbox to repack it. A restore can reintroduce an old object in a later pack with a different delta representation. Simply joining those object sections can produce conflicting delta references. The increments therefore store whole compressed objects, with zlib compression but no delta packing.

The exporter joins the packed-object sections, replaces their individual pack headers with one total object count, and calculates a new SHA-1 trailer checksum. Those fields come from Git’s pack format. We trade some compression efficiency for a download assembled directly from storage. The result is an ordinary bundle you can clone, including the saved ancestry:

git clone -b main mainbrella-app.bundle expense-tracker
cd expense-tracker
git log --oneline

The repository URL box skipped a decision

A downloadable bundle gives users an exit, but requiring a manual clone and push is a poor way to connect an app they’re still building. So we added GitHub authorization and linking. Here’s our first dialog. The repository field asks for owner/repository or a GitHub URL, with main already entered as the branch.

The first web change had a connection form, and the backend change had the transfer machinery. But knowing a repository’s URL doesn’t answer which GitHub account should grant access, whether the organization permits the app, or which repositories the customer wants it to see. We had made the user supply the destination before helping them establish access to it.

We compared that dialog with these screenshots of the ChatGPT Codex Connector on GitHub. Its installation screen starts with the account: my personal account appears alongside the organizations where I might install the app. Some entries offer configuration of an existing installation. The choice is visible, rather than hidden behind a URL someone has to remember.

The connector’s settings then show another decision: All repositories or Only select repositories. The screenshot has selected access enabled, a repository selector, and the repositories already granted. GitHub documents this installation flow for third-party apps. It’s the appropriate place to make the grant, under GitHub’s account and organization rules.

We gave our agent the first dialog and both connector screenshots and asked it to fix the flow. The revised Projects UI starts with app installation, lets GitHub handle personal-account or organization selection and repository grants, then returns to a picker of writable repositories. The picker uses the repository’s default branch, which the user can change for the transfer. Manage repository access takes them back to GitHub when they need another account or repository. The screenshots made the missing decisions concrete enough to implement.

The picker needs the same authority as the write

We borrowed the account and repository selection sequence. Mainbrella’s permissions have a narrower scope than those shown in the connector screenshot. We already have a read-only Import GitHub App; silently adding write access would change what its customers agreed to. We use a separate Mainbrella Build app requesting Contents write and Metadata read. Its registration manifest doesn’t request workflow permissions.

Installation and user authorization are distinct steps. Installation grants the app access to selected repository resources; authorization lets it act on the user’s behalf. We use GitHub App user access tokens, whose rights are constrained by both the app’s and the user’s permissions. An organization installation must not let a read-only member write through our Builder.

The repository discovery code follows the user’s installations and lists their repositories. It filters for our Build app, active installations with Contents write, and repositories where the user can push. Archived and disabled repositories are excluded. Pagination spans installations as well as repositories; a page with no eligible results can still have another page to fetch. A repository picker assembled from “everything this user can read” would offer destinations the eventual commit could never use.

Before linking, the backend checks user push permission and probes Git’s receive-pack service to check the app’s write grant too. OAuth state is single-use, expires, and is bound to the signed-in Mainbrella user and project; the code exchange uses PKCE. Credentials are encrypted in D1 with AES-GCM and stay in the API Worker. The sandbox receives repository objects and a checkout, without the access token. Linking therefore doesn’t put a publishing credential where generated application scripts run.

We also hit a local 503 on /github/build/repositories while reviewing this work. The configuration endpoint returned {"enabled":false}: the request stopped before reaching GitHub because our local backend didn’t have the Build app’s credentials. Build needs its own client ID, client secret, app slug, and encryption key. The setup instructions cover registration and the D1 migration. The flow is implemented, and we’re still working through integration fixes.

Confirm the transfer, then turn off hosted Git

Authorization alone doesn’t switch storage. The final link request locks the project against new Builder turns while it transfers history. We refuse to start that handoff during an active build: the expense tracker shouldn’t acquire a new hosted commit halfway through moving its head.

For a project with saved Git history, the destination branch must be empty or already at our saved commit. The Worker exports the bundle chain and streams its pack through Git’s HTTP receive-pack protocol. It checks the response and reads the branch back to confirm the expected SHA. We transfer the original Git objects, preserving their hashes and ancestry. We don’t recreate the expense tracker’s history as a single “imported files” commit.

Draft edits saved after the last checkpoint are included in a subsequent commit. An unrelated existing branch is a conflict, rather than permission to overwrite someone’s work. A project with no saved history can instead import supported source from an existing GitHub branch, or begin in an empty repository. The migration code handles those different starting points.

  1. Transfer and verify on GitHub. Until that succeeds, the project keeps its hosted history.
  2. Publish the switch in D1. Save the GitHub repository, branch, and commit; clear the hosted heads and remove the old Git version rows in a database batch.
  3. Remove the old R2 history. Delete the project’s bundles/ and parts/. A durable cleanup flag lets scheduled reconciliation finish after a partial failure.

GitHub, D1, and R2 share no transaction. The order makes a failed transfer leave hosted Git available, and makes failed cleanup leave redundant bytes rather than a missing repository. A retry can recognize a history transfer already accepted at the same SHA; draft-transfer recovery checks the project marker, parent commit, and snapshot. The link handler publishes the storage change only after that work.

The next Builder commit goes to github.com

After linking, “add monthly totals” still runs through Builder’s edit-and-check workflow. The save function dispatches to GitHub as soon as it sees the linked repository. It doesn’t also write a hosted Git version.

// From saveBuildGitVersion; hosted storage follows this branch.
const project = await githubProject(env, params.userId, params.appId);
if (project?.github_repo)
  return saveGithubVersion(env, params, runtime, turn, files, verified);

The Worker compares the snapshot with the remote tree, uploads changed blobs, creates a tree and commit, and updates the linked branch with force: false. Using the old tree as the base preserves unrelated repository files; deletions apply to paths Builder manages. An existing .gitignore is preserved so the user’s rules aren’t replaced with our starter rules at every save. GitHub’s reference API enforces the fast-forward update, so a concurrent push can stop the save rather than be overwritten.

A commit can reach GitHub before its acknowledgement reaches D1. Builder includes its turn ID in the commit message and, on retry, checks the remote head’s message and parent before accepting it as that turn’s result. That is a much narrower claim than “any retry is safe”: a head moved by another writer is a conflict.

The other writer might be the customer in their editor. At the next Builder turn, we read the linked branch and compare three versions of each supported source file: the last known GitHub version, the working draft, and the new remote version. Changes to different files can be combined. If both sides changed the same file differently, we stop and report the path, preserving the draft and leaving the GitHub pointer alone. This is a file-level comparison, not a line-level Git merge. Builder’s source limits still apply; the current importer allows at most 80 supported text files, each at most 64 KiB.

Version browsing and restores also use GitHub for a linked project, with commit SHAs as version IDs and reads limited to the linked branch’s reachable history. Revoked access, branch protection, or an unavailable GitHub API stops the operation. Falling back to R2 would silently restart the hosted Git costs the customer just opted out of, and leave them wondering which history contains their work.

Turning off our Git removes the hosted history storage and write costs. It doesn’t make an ongoing Builder session storage-free or compute-free. That’s the useful boundary: the expense tracker can begin with no GitHub account, acquire ordinary Git history from its first build, and later put that same history in a repository the customer controls. When they open it in their editor and run git log, the earlier work should still be there—and the next Builder commit should be there too.
